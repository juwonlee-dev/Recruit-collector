# Recruit Collector

채용 사이트(사람인, 잡코리아, 원티드, 리멤버, 점핏)의 검색 결과 목록을 주기적으로 크롤링해 DB에 적재합니다. 개인·비상업용입니다.

- **신규** 공고 → 추가 (`CREATED`)
- **기존** 공고 → 내용이 바뀌면 갱신하고 변경 전후 값을 이력으로 남김 (`UPDATED`)
- **사라진** 공고 → 행을 지우지 않고 `status=DELETED`로 변경 (`DELETED`)
- 삭제된 공고가 다시 보이면 → `ACTIVE`로 복구 (`REACTIVATED`)

## 도커로 배포 (PostgreSQL)

조회 서버(`app`), 수집기(`worker`, 자동 수집과 '지금 수집' 실행), PostgreSQL(`db`)을 도커 컨테이너로 띄웁니다. DB 데이터는 도커 볼륨 `recruit-collector_pgdata`에 저장되어 컨테이너를 내렸다 올리거나 이미지를 다시 만들어도 남습니다.

```bash
cp .env.example .env              # POSTGRES_PASSWORD를 정함 (git에 올리지 않음)
cp config.example.yaml config.yaml
docker compose up -d --build      # 배포·코드 변경 반영 (http://<PC 주소>:8765)
docker compose ps                 # 상태 (app은 healthy가 되면 준비 완료)
docker compose logs -f app        # 로그
docker compose up -d --build app  # 화면만 다시 배포 (진행 중인 수집에 영향 없음)
docker compose up -d --build worker   # 수집기 다시 배포 (진행 중인 수집이 끝날 때까지 최대 9분 30초 기다림)
docker compose kill -s SIGINT worker  # 수집기 강제 중지: 진행 중인 수집을 바로 CANCELED로 정리하고 종료 (꺼진 채로 남음 → up -d worker)
docker compose logs -f worker     # 수집 로그
docker compose down               # 중지 (데이터는 볼륨에 남음)
docker compose exec app recruit-collector --config /app/config.yaml login-off   # CLI 명령은 컨테이너 안에서
```

- `config.yaml`(읽기 전용)과 `config/` 폴더(설정 화면에서 고치는 검색 필터·키워드·지역)는 이미지에 넣지 않고 컨테이너에 연결합니다. 코드를 바꾸면 `docker compose up -d --build`로 다시 만들고, `config/`의 파일은 다시 만들 필요 없이 다음 수집부터 반영됩니다.
- DB 주소는 컨테이너의 환경 변수 `DATABASE_URL`로 넘기며, 있으면 `config.yaml`의 `database_url`보다 우선합니다.
- 모든 컨테이너가 `restart: unless-stopped`라 도커(Docker Desktop)가 켜지면 함께 다시 뜹니다. PC 부팅 때 Docker Desktop이 자동 시작되도록 설정해 두세요.
- PostgreSQL 포트(5432)는 이 PC(127.0.0.1)에서만 열립니다. 외부에는 조회 화면 포트(8765)만 열립니다.
- 앞단에 https 프록시(Caddy 등)를 둘 때를 위해 `FORWARDED_ALLOW_IPS: "*"`로 프록시의 `X-Forwarded-Proto`를 믿습니다(구글 로그인 콜백 주소를 https로 만들기 위함).
- **주의**: `docker compose down -v`는 DB 볼륨까지 지웁니다.

### 수집기 (worker)

수집은 조회 화면과 분리된 `worker` 컨테이너(`recruit-collector worker`, `recruit_collector/worker.py`)가 합니다. 둘은 DB로만 주고받으므로(`recruit_collector/crawl_queue.py`) **조회 화면을 다시 배포해도 진행 중인 수집은 계속됩니다.** 수집기는 하나만 띄웁니다.

- **자동 수집**: 설정 > 스케줄러에서 바꾼 켜짐 여부·주기(DB `app_settings`)를 수집기가 2초마다 확인해 스케줄러에 반영합니다. 화면의 다음 수집 시각은 같은 주기로 계산합니다.
- **지금 수집**: 조회 화면은 요청을 대기열(`crawl_requests`, `PENDING`)에 넣기만 하고, 수집기가 2초 안에 가져가 수집합니다(`STARTED`, 그 사이에 자동 수집이 먼저 시작했으면 `SKIPPED`). 수집기가 꺼져 있으면 요청이 대기열에 남아 있다가(화면에 `대기 중`) 수집기가 뜨면 실행됩니다. 한 사이트에 대기 중인 요청은 하나뿐이라(DB 부분 유니크 인덱스) 이미 대기 중이거나 수집 중이면 다시 요청할 수 없습니다(409).
- **수집기 상태**: 수집기는 10초마다 살아 있다는 신호(`app_settings.worker_heartbeat`)를 남깁니다. 1분 넘게 신호가 없으면 수집 상태 영역과 설정 > 스케줄러에 `수집기가 꺼져 있습니다`를 보여줍니다. 도커 healthcheck도 이 신호로 봅니다.
- **수집기 재배포·중지(SIGTERM)**: 새 수집은 받지 않고, 진행 중인 수집이 끝날 때까지 최대 9분 30초(`WORKER_STOP_TIMEOUT`) 기다린 뒤 종료합니다. 그래도 남아 있으면 `CANCELED`(수집기 종료 대기 시간이 지나 중단됨)로 정리하고 끝냅니다. 도커는 10분(`stop_grace_period`)까지 기다립니다.
- **강제 중지(SIGINT)**: `docker compose kill -s SIGINT worker`를 보내면(또는 기다리는 중에 종료 신호를 한 번 더 보내면) 진행 중인 수집을 바로 `CANCELED`(수집기를 강제로 종료하여 중단됨)로 정리하고 끝냅니다. 강제 중지한 수집기는 꺼진 상태로 남으므로(자동으로 다시 뜨지 않음) 이어서 `docker compose up -d worker`(코드를 바꿨으면 `--build`)로 다시 띄웁니다. 꺼져 있는 동안의 '지금 수집' 요청은 대기열에 남았다가 실행됩니다.
- 수집기가 뜰 때 이전 수집기에서 하다 끊긴 `RUNNING` 기록은 `CANCELED`로 정리합니다(아래 '조회 화면' 참고).

### HTTPS (Nginx + 무료 인증서 자동 갱신)

`nginx` 컨테이너가 앞단에서 HTTP(PC 8765)와 HTTPS(PC 8766)를 받아 `app`으로 넘기고, `certbot` 컨테이너가 인증서를 발급·갱신합니다. 공유기는 외부 80 → PC 8765, 외부 443 → PC 8766으로 포트포워딩합니다(발급·갱신 확인이 외부 80으로 옵니다).

- `.env`의 `DOMAIN`으로 인증서를 받습니다. 인증서가 없으면 1시간마다 발급을 시도하고, 있으면 12시간마다 `certbot renew`로 만료 30일 전부터 갱신합니다. nginx는 1분마다 인증서 파일을 확인해 바뀌면 HTTPS를 켜고 설정을 다시 읽습니다(`nginx/40-ssl-watch.sh`).
- 인증서가 생기면 서비스 도메인의 http 접속은 https로 이동합니다. 다른 주소(예전 주소 등)는 http 그대로 조회 서버로 전달합니다.
- 기본은 Let's Encrypt입니다. `kro.kr`처럼 여러 사람이 나눠 쓰는 도메인은 Let's Encrypt의 도메인당 주간 발급 한도(50장)를 함께 써서 발급이 막힐 수 있습니다. 그럴 때는 ZeroSSL 대시보드(Developer > EAB Credentials)에서 받은 값을 `.env`의 `ZEROSSL_EAB_KID`·`ZEROSSL_EAB_HMAC_KEY`에 넣고 `docker compose up -d certbot`을 실행하면 ZeroSSL에서 발급받습니다(갱신도 ZeroSSL).
- 상태 확인: `docker compose logs certbot`, `docker compose logs nginx | grep ssl`
- 인증서와 계정은 도커 볼륨 `recruit-collector_certs`에 남습니다.

백업과 복원:

```bash
docker compose exec -T db pg_dump -U recruit -Fc recruit > backup.dump
docker compose exec -T db pg_restore -U recruit -d recruit --clean --if-exists < backup.dump
```

### SQLite에서 옮기기

예전 SQLite DB(`data/recruit.db`)의 모든 표를 id 그대로 PostgreSQL로 옮기고, 끝나면 모든 행을 원본과 비교해 검증합니다(`recruit_collector/migrate.py`). 원본은 읽기 전용으로 열어 바꾸지 않고, 복사는 한 트랜잭션이라 실패하면 대상에 아무것도 남지 않습니다. 옮기는 동안 SQLite를 쓰는 서버는 꺼 두세요.

```bash
docker compose up -d db
docker compose stop app
DATABASE_URL=postgresql+psycopg://recruit:<비밀번호>@127.0.0.1:5432/recruit \
  python -m recruit_collector migrate-sqlite data/recruit.db   # 대상에 공고가 이미 있으면 --replace
docker compose up -d
```

## 실행 (도커 없이)

```bash
python -m venv .venv
.venv/Scripts/pip install -e ".[dev]"     # macOS/Linux: .venv/bin/pip
cp config.example.yaml config.yaml          # 공통 설정 (DB·주기·HTTP)

python -m recruit_collector run-once                      # 1회 수집
python -m recruit_collector run-once --search <name>      # 특정 조건만
python -m recruit_collector worker                        # 수집기: 자동 수집 + '지금 수집' 처리 (serve와 함께 띄움, 하나만)
python -m recruit_collector serve                         # 조회 화면 http://127.0.0.1:8000 (0.0.0.0으로 열려 같은 네트워크의 다른 기기에서도 접속 가능)
python -m recruit_collector build-catalog                 # 필터 생성용 직무·지역 목록(매핑 데이터) 갱신
python -m recruit_collector login-off                     # 조회 화면의 로그인 사용 끄기 (관리자로 로그인할 수 없게 된 경우 복구용)
pytest
```

자동 수집은 조회 화면(`serve`)의 **설정 > 스케줄러** 탭에서 시작·중지하고 주기를 바꾸며, 실제 수집은 수집기(`worker`)가 합니다. 수집기를 띄우지 않으면 자동 수집과 '지금 수집'이 진행되지 않습니다(요청은 대기열에 남음). SQLite는 WAL 모드라 수집 중에도 조회할 수 있습니다.

## 설정 파일

| 파일 | 내용 |
|---|---|
| `config.yaml` | DB·수집 주기·HTTP 등 공통 설정과 아래 파일들의 위치(`paths`) |
| `config/searches/<사이트>.yaml` | 사이트(크롤러 모듈)별 검색 필터. 파일 이름이 사이트이고, 파일 하나에 검색 조건 여러 개를 둘 수 있습니다 |
| `config/keywords.yaml` | 필터 생성에 쓰는 키워드 (설정 화면에서 등록·삭제) |
| `config/regions.yaml` | 필터 생성에 쓰는 지역 (설정 화면에서 등록·삭제) |
| `config/region_codes.yaml` | 공통 지역코드: 시도와 시군구 목록 (지역 선택지, 사이트별 지역 코드와 매핑하는 기준) |
| `config/catalog/<사이트>.json` | 필터 생성용 매핑 데이터: 사이트의 직무 선택지와 비교용 핵심어 |
| `config/catalog/<사이트>_regions.json` | 필터 생성용 매핑 데이터: 사이트의 지역 선택지 (시도 전체·시군구) |

검색 필터 파일은 **수집을 시작할 때마다** 새로 읽어 메모리에 올립니다(자동 수집·CLI·수동 수집 모두). 수집이 시작된 뒤에 파일을 바꿔도 진행 중인 수집은 시작 시점의 조건으로 끝나고, 바뀐 내용은 다음 수집부터 적용됩니다. 서버·스케줄러를 다시 띄울 필요는 없습니다. 파일은 임시 파일에 쓴 뒤 바꿔치기하므로 반쯤 쓰인 파일을 읽는 일은 없습니다.

### 키워드로 검색 필터 생성

조회 화면 `설정` 메뉴에서 키워드를 등록·삭제하고 `필터 생성`을 누르면, 키워드를 사이트별 직무 필터로 바꿔 각 검색 필터 파일의 직무 필드에 반영합니다(`recruit_collector/filters.py`).

1. **매핑 데이터**: 각 크롤러 모듈이 사이트 검색 화면의 직무 선택지를 가져옵니다(IT·개발 분류 안만). 선택지 이름을 비교용 핵심어로 나눠 `config/catalog`에 저장합니다. 없으면 필터 생성 때 자동으로 받고, `사이트에서 직무 목록 새로 받기`를 체크하거나 `build-catalog`로 갱신할 수 있습니다.

   | 사이트 | 직무 선택지 출처 | 범위 | 필드 |
   |---|---|---|---|
   | 사람인 | 직무별 공고 화면(`/zf_user/jobs/list/job-category`)에 포함된 옵션 JSON | IT개발·데이터 | `job_keywords` |
   | 잡코리아 | 검색 화면이 쓰는 직무 분류 주소(`/Search/api/codes/jobClassification`) | AI·개발·데이터 | `duties` |
   | 원티드 | 직군 목록 화면(`/wdlist/518`)의 `__NEXT_DATA__` | 개발 | `job_ids` |
   | 리멤버 | 화면이 쓰는 필터 선택지 주소(`open-profile-api…/v2/open_profiles/options`) | SW개발 | `job_categories` |
   | 점핏 | 화면이 쓰는 코드 주소(`jumpit-api…/api/common/code-initialize`)의 `jobCategory` | 전체(개발 직무만 있음) | `job_categories` |

2. **핵심어 비교**: 이름을 `/`·`·`·`,`로 나누고 공백과 끝의 일반어(개발자·개발·엔지니어 등)를 뗀 것을 핵심어로 씁니다. 키워드 쪽은 동의어(백엔드=서버, Java=자바 등)로 넓힌 뒤, 핵심어가 **정확히 같은** 선택지를 고릅니다. 부분 일치를 쓰지 않으므로 '웹개발'이 '웹퍼블리셔'·'웹마스터'까지 잡지는 않습니다.

   | 선택지 | 핵심어 | 걸리는 키워드 |
   |---|---|---|
   | 사람인 백엔드/서버개발 | 백엔드, 서버 | 백엔드 개발, 서버 개발 |
   | 원티드 자바 개발자 | 자바 | Java |
   | 잡코리아 웹개발자 | 웹 | 웹개발 |

3. **반영**: 직무 필드만 바꾸고 지역·`max_pages`·검색 조건 이름은 그대로 둡니다. 맞는 직무가 하나도 없는 사이트는 파일을 바꾸지 않습니다(직무 필터가 비면 전체 공고를 수집하게 되므로). 마지막 생성 기록은 파일의 `generated`에 남습니다(수집에는 쓰지 않음). 직무 필터는 OR 조건이라 순서만 다르면 `변경 없음`으로 봅니다.

동의어는 `filters.SYNONYMS`, 직무 후보 범위는 각 크롤러 모듈의 `JOB_SCOPE`에서 바꿀 수 있습니다. 파일을 직접 고쳐도 되지만, 필터 생성은 YAML을 다시 쓰므로 직접 단 주석은 사라집니다.

### 지역으로 검색 필터 생성

`설정` 메뉴의 키워드 아래 `지역`에서 시도(전체) 또는 시군구를 골라 등록하면, `필터 생성` 때 사이트별 지역 코드로 바꿔 각 검색 필터 파일의 지역 필드에 반영합니다(`recruit_collector/regions.py`). 등록한 지역이 없으면 지역 필드는 그대로 둡니다.

- **공통 지역코드** (`config/region_codes.yaml`): `시도` 또는 `시도 시군구` 형식(예: `서울`, `경기 안양시`). 구가 있는 시는 시 단위로 묶습니다(안양시 = 동안구 + 만안구). 시도 전체를 등록하면 그 시도의 시군구 등록은 겹치므로 지웁니다.
- **사이트별 지역 선택지**: 직무와 같이 필터 생성 때 없으면 받아 `config/catalog/<사이트>_regions.json`에 저장합니다.

  | 사이트 | 지역 선택지 출처 | 필드 | 예: 경기 안양시 |
  |---|---|---|---|
  | 사람인 | 검색 화면에 포함된 지역 JSON(`area`) | `locations`(시도 전체, loc_mcd) / `districts`(시군구, loc_cd) | `districts: [102320]` |
  | 잡코리아 | 검색 화면의 `CODES.area` | `locations` | `B240`(동안구), `B250`(만안구) |
  | 원티드 | 직군 목록 화면 `__NEXT_DATA__`의 `filterData` | `locations` | `gyeonggi.anyang-si` |
  | 리멤버 | 필터 선택지 주소의 `addresses` | `addresses` | `[경기도, 안양시 동안구]`, `[경기도, 안양시 만안구]` |
  | 점핏 | 코드 주소의 `locationTag` (사람인과 같은 코드 체계) | `location_tags`(시도 전체·시군구 모두) | `102320` |

- **매핑 규칙**: 사이트마다 다른 시도 이름(서울특별시·서울, 경기도·경기)은 `region_names.SIDO_KEYS`로 맞추고, 시군구는 이름으로 맞춥니다. 시 이름과 같은 선택지가 있으면 그것만(사람인 '안양시'), 없으면 그 시의 구를 모두 씁니다. 광주·전남은 사람인·잡코리아처럼 `전남광주`로 묶고 원티드·리멤버에서는 광주·전남 두 곳으로 매핑합니다. 행정구역은 현재 이름(2026년 인천 개편 등)을 쓰고, 옛 이름만 있는 사이트는 `region_names.OLD_NAMES`의 옛 구역으로 매핑합니다(예: 인천 영종구 → 옛 중구, 그만큼 넓게 수집). 사이트에 없는 지역(예: 원티드의 계룡시)은 결과에 `맞는 지역 없음`으로 표시하고 그 사이트에서는 쓰지 않습니다.
- 사람인은 시도 전체(`loc_mcd`)와 시군구(`loc_cd`)를 함께 주면 OR로 합쳐집니다.

## 현재 수집 범위 (`config/searches`)

관심 키워드(백엔드 개발, 서버 개발, 유지보수, 웹개발, 풀스택, Java)를 **자유 검색어가 아니라 각 사이트의 직무 필터**로 지정합니다. 필터는 여러 개를 고르면 OR로 동작하므로 사이트당 검색 조건 1개로 한 번에 조회합니다. 자유 검색어는 키워드마다 따로 검색해야 하고(쉼표로 묶으면 AND), 겹치는 공고를 여러 번 받아오게 됩니다.

| | 지역 | 직무 |
|---|---|---|
| 사람인 | `loc_mcd` 101000(서울 전체), 102000(경기 전체) | `cat_kewd` 84(백엔드/서버개발), 87(웹개발), 2232(풀스택), 235(Java), 89(유지보수) |
| 사람인(헤드헌팅) | 사람인과 같음 (`config/searches/saramin_hh.yaml`) | 사람인과 같음 |
| 잡코리아 | `searchBarLocal` 쿠키 I000(서울 전체), B000(경기 전체) | `duty` 1000229(백엔드개발자), 1000231(웹개발자) |
| 원티드 | `locations` seoul.all, gyeonggi.all | 개발(518) > `job_ids` 872(서버 개발자), 873(웹 개발자), 660(자바 개발자) |
| 리멤버 | `addresses` 서울특별시, 경기도 | SW개발 > 백엔드, 풀스택 |
| 점핏 | `location_tags` 101000(서울 전체) 등 시도 전체 | `job_categories` 1(서버/백엔드 개발자), 15(SW/솔루션) |

사이트마다 직무 분류가 달라, 관련 필터가 없는 키워드는 그 사이트에서 사용하지 않습니다. 위 직무 필터는 키워드 6개로 `필터 생성`을 실행한 결과와 같습니다.

사이트(크롤러)별로 병렬 수집(같은 크롤러 안에서는 순차)하므로 1회 수집 시간은 가장 오래 걸리는 잡코리아(약 115페이지, 5분 남짓)에 맞춰지며, 매시 정각으로 설정했습니다.

### 사이트별 수집 방식

| 사이트 | 방식 | 등록일 | 마감일 | 헤드헌팅 구분 |
|---|---|---|---|---|
| 사람인 | 검색 결과 HTML 파싱 | 날짜만 (일부 추정) | O | 크롤러를 나눔 (`company_cd`) |
| 잡코리아 | 검색 페이지에 포함된 Next.js 쿼리 상태(JSON) 파싱 | O | O | `userRefType` = `S` |
| 원티드 | 목록 화면이 호출하는 내부 JSON 주소(`/api/chaos/navigation/v1/results`) | **없음** | **없음** | **없음** |
| 리멤버 | 목록 화면이 호출하는 내부 JSON 주소(`career-api…/job_postings/search`, POST) | O | O | `job_posting_type` = `internal_headhunter` |
| 점핏 | 목록 화면이 호출하는 내부 JSON 주소(`jumpit-api…/api/positions`, 페이지당 16건) | **없음** | O (`alwaysOpen`이면 상시채용) | **없음** (기업 직접 공고만) |

원티드·리멤버·점핏은 목록 페이지 HTML에 공고가 없고 화면이 내부 JSON 주소를 호출해 그리므로, 같은 주소를 화면과 같은 조건으로 요청합니다. 공개 약속이 없는 주소라 사이트 개편 시 바뀔 수 있습니다. 모든 사이트에 같은 요청 간격(2~4초 무작위)을 적용하며, 간격은 도메인별로 프로세스 전체가 공유합니다(사람인과 사람인(헤드헌팅)처럼 같은 사이트를 두 크롤러가 동시에 수집해도 사람인에는 간격을 지켜 하나씩 요청). 또 차단되면 우회하지 않고 해당 실행을 실패로 기록합니다.

### 경력(연차) 정규화

사이트마다 경력 표기와 검색 필터의 연차 범위가 달라, 각 크롤러가 수집 시점에 경력 조건을 `career_min`(최소 연차) / `career_max`(최대 연차, 없으면 상한 없음) / `career_any`(경력무관)로 정규화해 적재합니다. 연차는 0부터 시작하며 신입 = 0년차입니다.

| 원본 예 | 정규화 |
|---|---|
| 신입 | 0 ~ 0 |
| 경력3년↑ / 잡코리아 경력(최소 3년) / 원티드 3~100 | 3 ~ 상한 없음 |
| 경력 3~10년 / 리멤버 3~10 / 점핏 minCareer~maxCareer | 3 ~ 10 |
| 경력5년↓ | 1 ~ 5 |
| 리멤버 ~3년 이하(최소값 없음) | 0 ~ 3 |
| 신입·경력 / 원티드 신입 가능(is_newbie) / 점핏 newcomer | 0 ~ … |
| 경력무관 (사람인·잡코리아 표기, 리멤버 최소·최대 모두 없음) | `career_any` |

원티드는 경력무관을 따로 표시하지 않아 범위로만 저장합니다.

조회 화면의 지역 필터는 설정의 지역 등록과 같은 **시도·시군구**(공통 지역코드)로 고르며, 여러 지역을 함께 고르면 하나라도 맞는 공고를 보여줍니다(예: 서울 전체 + 경기 전체, 서울 강남구 + 서울 강서구). 시도 전체를 고르면 그 시도의 시군구는 고를 수 없습니다(이미 포함). 공고마다 지역 표기를 공통 지역코드로 바꿔 `job_postings.regions`(`|서울|서울 강남구|`)에 저장해 두고 그 값으로 찾습니다(`recruit_collector/region_names.py`). 사이트마다 표기가 달라(잡코리아 `서울 강남구, 경기 안양시 동안구`, 사람인 `서울전체 , 강남구 , 경기 광명시 , 안양시`처럼 시도를 이어 쓰는 형식) 단순 부분 일치로는 시군구를 정확히 찾을 수 없기 때문입니다. 구는 시 단위로 묶고(안양시 동안구 → 안양시), 리멤버처럼 대표 지역만 있는 공고(`경기 성남시 외 1`)는 표기된 지역으로만 찾습니다. 컬럼이 생기기 전에 수집한 공고는 DB를 열 때 채웁니다.

조회 화면의 연차 필터(신입, 1~3년차, 4~6년차, 7~9년차, 10년차 이상)는 **공고의 연차 범위가 선택한 구간과 겹치면** 보여주고, **경력무관 공고는 어떤 구간을 골라도 포함**합니다. `경력무관`을 고르면 경력무관 공고만 보여줍니다. 여러 구간을 함께 고르면 하나라도 맞는 공고를 보여줍니다.

조회 화면의 고용형태 필터는 사람인·잡코리아·원티드의 고용형태 선택지를 합친 목록입니다: 정규직, 계약직, 인턴, 파견직, 도급, 프리랜서, 아르바이트, 연수생·교육생, 병역특례, 위촉직·개인사업자. 여러 개를 고르면 하나라도 맞는 공고를 보여줍니다. 사이트마다 표기가 달라 비슷한 표기를 묶습니다(계약직 ← 기간제·무기계약직, 인턴 ← 인턴직, 아르바이트 ← 파트, 병역특례 ← 전문연구요원·산업기능요원·보충역·현역). `employment_type`(잡코리아 `정규직, 계약직`, 사람인 `정규직·계약직`)을 항목 단위로 맞추므로 `파견직 (정규직 전환가능)`은 정규직이 아니라 파견직으로 찾습니다. 리멤버 공고는 고용형태를 수집하지 않아 고용형태를 고르면 빠집니다. 선택지는 `web/app.py`의 `EMPLOYMENT_TYPES`에서 바꿀 수 있습니다.

조회 화면의 헤드헌팅 필터는 `헤드헌팅 포함`(기본), `헤드헌팅만`, `헤드헌팅 제외`이고, 헤드헌팅 공고에는 회사명 옆에 `헤드헌팅` 표시를 붙입니다(`job_postings.headhunting`). 잡코리아·리멤버는 목록 데이터에 공고를 올린 쪽이 서치펌인지 나와 있어 그대로 씁니다. 사람인은 목록 HTML에 표시가 없어서 **크롤러를 둘로 나눕니다**: `사람인`(`saramin`)은 헤드헌팅을 뺀 일반·파견(`company_cd=0,1,2,3,4,5,6,7,9`)만, `사람인(헤드헌팅)`(`saramin_hh`, 검색 필터 파일 `config/searches/saramin_hh.yaml`)은 헤드헌팅(`company_cd=10`)만 검색합니다(두 검색의 전체 건수 합이 기업 형태 조건 없이 검색한 건수와 같음). 두 크롤러는 검색 필터 파일·수집 기록·`지금 수집`이 따로이고, 공고는 둘 다 플랫폼 `사람인`(`job_postings.site = saramin`)으로 저장됩니다(`Crawler.platform`). 필터 생성의 매핑 데이터도 사람인 것을 같이 씁니다. 기업 형태(`company_types` → `company_cd`)는 크롤러의 **고정 조건**(`Crawler.fixed_condition`)이라, 설정의 `필터 생성`이 검색 필터 파일에 항상 이 값을 다시 써 넣고(설정 화면에 `고정`으로 표시), 파일을 손으로 바꿔도 수집할 때는 크롤러 값을 씁니다. 원티드는 구분이 없어 모두 일반 공고로 둡니다. 컬럼이 생기기 전에 수집한 잡코리아·리멤버 공고는 DB를 열 때 원본(`raw`)으로 채우고(원티드는 일반), 사람인 공고는 다음 수집 때 채워집니다.

### 공고의 시각 정보

| 컬럼 | 의미 | 정렬 |
|---|---|---|
| `posted_at` | 채용 사이트에 공고가 등록된 시각 | 최근 등록순 (기본) |
| `last_seen_at` | 해당 공고가 담긴 목록 페이지를 가장 최근에 가져온 시각 | 최근 수집순 |
| `updated_at` | 내용이 마지막으로 바뀐 시각. 처음 수집 시에는 수집 시각 | 최근 변경순 |
| `deadline_at` | 마감일. 상시채용·채용시 마감은 없음(맨 뒤) | 마감 임박순 |

등록 시각은 사이트마다 정밀도가 다릅니다.

- **잡코리아**: 목록 데이터의 `createdAt`(초 단위)
- **리멤버**: 목록 데이터의 `starts_at`
- **원티드**: 목록 데이터에 등록일이 없어 비어 있습니다(최근 등록순에서 뒤로)
- **사람인**: 목록에 날짜만 표시됩니다(`등록일 26/11/04`). `수정일`만 표시된 공고는, 공고 ID가 등록 순서대로 증가하는 점을 이용해 ID가 바로 아래인 공고의 등록일을 하한으로 추정합니다(화면에 "추정" 표시). 이후 실제 등록일이 보이면 교체합니다.

## 조회 화면

- 상단의 공고 수와 검색 조건별 수집 상태(진행률, 결과, 다음 수집 예정)는 채용 플랫폼별 카드로 묶어 보여주며(사람인 카드 안에 일반 공고·헤드헌팅 크롤러), 상태는 새로고침 없이 갱신됩니다. 수집 중에는 5초, 대기 중에는 30초마다 `/api/status`를 확인하고, 탭이 보이지 않으면 멈춥니다.
- 검색창과 결과 목록은 자동으로 바뀌지 않으며 `조회`를 누른 시점의 데이터를 보여줍니다.
- **수동 수집**: 수집 상태의 크롤러마다 `지금 수집` 버튼이 있어, 해당 크롤러의 검색 조건 전체를 수집합니다. 요청은 대기열에 들어가고 수집기가 가져가 자동 수집과 같은 과정(`runner.run_site`)으로 진행하며 실행 기록에 `수동`으로 남습니다. 수집기가 꺼져 있으면 `대기 중`으로 남았다가 수집기가 뜨면 시작합니다. `POST /api/crawl/{site}`로도 요청할 수 있습니다.
- **자동 수집 (설정 > 스케줄러)**: `자동 수집 시작`/`중지`와 수집 주기(30분·1시간·2시간·3시간·6시간·12시간·매일 9시·매일 9시와 18시, 또는 cron 직접 입력)를 바꿉니다. 정해진 시각마다 사이트별 수집을 `지금 수집`과 같은 방식으로 시작하고(실행 기록에 `자동`), 이미 수집 중인 사이트는 그 회차를 건너뜁니다. 켜짐 여부와 주기는 DB(`app_settings`)에 저장되어 서버를 다시 띄워도 유지되며, 처음 주기는 `config.yaml`의 `schedule.cron`입니다. 수집 대상 사이트에 부담을 주지 않도록 간격 30분 미만의 주기는 받지 않습니다. 수집 상태 영역에 다음 수집 시각(또는 `자동 수집 꺼짐`)이 표시됩니다.
  - 같은 사이트가 이미 수집 중이거나(자동·수동·CLI 모두) '지금 수집' 요청이 대기 중이면 거절합니다(409).
  - 수집 중인 실행은 페이지마다 진행 기록(`heartbeat_at`)을 남깁니다. 10분 넘게 기록이 없으면 프로세스가 중단된 것으로 보고 `중단됨`으로 표시하며, 다시 수집할 수 있습니다.
  - 수집기가 다시 뜨면(배포·재시작) 이전 수집기에서 하던 자동·수동 수집은 함께 끝났으므로, 남아 있던 `RUNNING` 기록을 `CANCELED`(취소됨)로 정리합니다. 조회 화면을 다시 띄우는 것은 수집과 관계없어 정리하지 않습니다. 끝난 시각은 마지막 진행 기록 시각이고, 오류 칸에 사유를 남깁니다. CLI 수집은 다른 프로세스일 수 있어 진행 기록이 끊긴 것만 정리합니다. 중단된 수집은 마지막 반영 전에 끊긴 것이라 공고 데이터에는 영향이 없습니다.
- **리뷰·연봉 버튼** (공고 목록·상세의 회사명 옆):
  - `리뷰`: 잡플래닛 검색 링크를 모달로 보여줍니다. 잡플래닛은 수집기 요청을 봇 차단(Cloudflare)으로 막으므로 리뷰를 가져오지 않고, 내 브라우저에서 열도록 합니다.
  - `연봉`: [올댓컴퍼니](https://allthatcompany.com)(국민연금 가입 사업장 자료 기반)에서 회사의 월별 총인원·입사자·퇴사자·월평균급여(추정)를 **열 때마다** 가져와 차트로 보여줍니다(저장하지 않음). 기간(1년·3년·전체), 요약 수치, 표로 보기를 제공합니다.
  - 회사 찾기: 법인 표기·괄호 안 내용·공백을 뺀 회사명으로 검색해(앞 2페이지) **회사명과 주소가 모두 같은 회사**를 먼저, 없으면 **회사명이 같은 회사**를 고릅니다. 공고에는 근무지가 시·도·시·군·구까지만 있어 주소는 회사 주소가 공고 근무지역으로 시작하는지로 비교합니다(예: `서울 구로구` ↔ `서울특별시 구로구 디지털로26길`). 모달에서 검색 결과의 다른 회사를 직접 고를 수 있습니다.
- **연봉·인원 자료의 출처** (`salary_sources.py`): 연봉 모달·연봉·인원 메뉴(검색·회사 페이지)·회사 비교 모두 올댓컴퍼니를 먼저 보고, 못 가져오면(삭제된 회사 페이지 404, 요청 실패, 같은 이름의 회사가 없음) **국민연금공단 공공데이터**(가입사업장 정보 오픈 API, `nps.py`)로 같은 모양의 자료를 보여줍니다. 화면 위에 대체한 이유를, 맨 아래에 실제 출처를 표시합니다.
  - 국민연금 자료: 회사명(법인 표기·띄어쓰기 제외)과 주소(시·도, 시·군·구)로 사업장을 찾고, 최근 12개월의 가입자수·신규취득자수(입사)·상실가입자수(퇴사)와 월평균급여(추정) = 당월고지금액 ÷ 보험료율(2025년까지 9%, 2026년부터 해마다 +0.5%p) ÷ 가입자수를 그립니다. 보험료는 기준소득월액 상한까지만 매겨 고소득자가 많으면 낮게 나옵니다. 한 달에 두 번 요청하므로 받은 달은 DB(`nps_months`)에 두고 다시 요청하지 않으며, 요청 사이 0.3초를 둡니다. 국민연금에서 찾은 회사의 ID는 `n` + 그 달 자료의 seq입니다(비교·즐겨찾기에도 사용).
  - 올댓컴퍼니에서 본 회사의 이름·주소는 DB(`atc_companies`)에 남겨, 회사 페이지·비교·공유 링크에서 그 회사를 못 가져와도 국민연금에서 찾을 수 있게 합니다. 삭제된 페이지는 하루 동안 다시 요청하지 않습니다.
  - **공시 기준 평균연봉** (`dart.py`): 모든 연봉 화면에 OpenDART 사업보고서 '직원 현황'의 직원 1인 평균 급여(부문·성별 직원 수로 가중 평균, 합계 행이 있으면 그 값)를 최근 3개 사업연도까지 보여줍니다(사업보고서 링크 포함). 회사명이 같은 공시 회사가 여럿이면 주소로 고릅니다. 사업보고서를 내지 않는 회사는 '공시 회사로 찾지 못함'. 회사 목록은 일주일, 직원 현황은 30일(자료 없음은 7일) DB(`dart_corps`, `dart_cache`)에 둡니다.
  - 인증키: `.env`의 `DATA_GO_KR_SERVICE_KEY`(공공데이터포털 일반 인증키, Encoding·Decoding 어느 쪽이든), `OPENDART_API_KEY`. 비우면 해당 자료 없이 동작합니다.
- **연봉·인원 메뉴** (`/salary`): 회사명으로 올댓컴퍼니를 검색해 회사명·주소 목록을 보고, 회사를 누르면 연봉 모달과 같은 화면을 페이지로 봅니다. 최근 검색어는 이 브라우저(localStorage)에만 최대 8개 저장되며, 넘치면 가장 오래된 것부터 지워지고 × 로 하나씩 지울 수 있습니다.
  - 회사 비교: 검색 결과의 `+ 비교`(또는 회사 페이지의 `다른 회사와 비교`)로 2~4곳을 비교함에 담고 `N곳 비교하기`를 누르면 `/salary/compare?ids=..`에서 나란히 봅니다(예전 `?a=..&b=..` 링크도 열림). 기간은 회사들의 자료를 합친 범위이고 자료가 없는 달은 그 회사만 비워 둡니다. 요약(두 곳이면 차이 A−B 포함, 좁은 화면은 지표마다 2열), 월평균급여·총인원(실제 인원 / 증감률 시작=100)·입사율·퇴사율(총인원 대비 비율) 차트, 지표별 표를 보여줍니다. 색은 칸(A~D)마다 고정이고 D는 주황과 색이 가까워 점선으로도 구분합니다. 비교 화면에서 회사를 빼거나(3곳 이상일 때) 추가할 수 있고, 올댓컴퍼니에는 동시에 2곳까지만 요청합니다. 비교함은 이 브라우저에만 기억합니다.
  - 공고 목록의 회사명을 누르면 그 회사명으로 연봉·인원 검색(`/salary?q=회사명`)을 바로 실행합니다(연봉·인원 메뉴를 쓸 수 있을 때만).
  - 공고의 `연봉` 모달에서도 `+ 비교하기`로 그 회사를 비교함에 담을 수 있습니다(연봉·인원 메뉴를 쓸 수 있을 때만: 로그인 사용이 꺼져 있거나 로그인한 상태). 2곳 이상이 되면 비교 분석으로 갈지 묻고, 가득 찼으면(4곳) 담긴 회사 중 뺄 곳을 골라 교체합니다(교체한 회사는 같은 칸·색).
- **즐겨찾기 (계정별)**: 로그인 사용이 켜져 있고 로그인한 경우에만 별(☆/★)이 보입니다. 공고 목록은 공고명 왼쪽, 연봉·인원 검색 결과는 회사명 왼쪽의 별을 눌러 지정·해제하고, 그때마다 화면 아래에 토스트 알림이 잠시 뜹니다(`static/favorite.js`). 공고는 `favorite_postings`(사용자·공고), 회사는 `favorite_companies`(사용자·올댓컴퍼니 회사 ID, 지정할 때의 회사명·주소)에 저장합니다. API: `PUT`(지정)·`DELETE`(해제) `/api/favorites/postings/{공고 ID}`, `/api/favorites/companies/{회사 ID}`(지정할 때 본문 `{"name", "address"}`).
  - **공고 보기 탭** (`/?view=fav`, `/?view=company`, `web/favorites.py`): 공고 페이지 위에 `전체 공고 | ★ 즐겨찾기 | 관심 회사 새 공고` 탭이 보입니다. 검색 조건·정렬은 탭 안에서 그대로 씁니다.
    - **즐겨찾기 탭**: 즐겨찾기한 공고만, 기본 마감 임박순. 마감·삭제되었거나 마감일이 지난 공고는 아래 `지난 공고`로 모읍니다. 위에 마감 임박(7일 이내)·최근 7일 변경·지난 공고 수를 보여줍니다.
    - **마감 D-day**: 즐겨찾기한 공고의 제목 옆 배지(어느 탭에서나). 오늘 마감·D-3 이하 빨강, D-7 이하 주황, 그 밖은 회색, 마감·삭제는 `마감·삭제됨`. 상시채용 등 마감일이 없으면 표시하지 않습니다.
    - **변경 알림**: 즐겨찾기한 뒤 최근 7일 안에 바뀌었거나(마감·제목·지역 등) 다시 올라온 공고에 `변경됨`(누르면 상세의 이력, 툴팁에 바뀐 항목).
    - **관심 회사 새 공고 탭**: 즐겨찾기한 회사와 회사명이 같은 진행 중 공고. 회사명은 법인 표기·괄호·띄어쓰기를 빼고 비교합니다(`job_postings.company_key`, `favorite_companies.name_key`). 회사를 즐겨찾기한 뒤 새로 수집된 공고에 `NEW`를 붙이고 탭 옆에 그 수를 보여줍니다. 탭을 보기만 해서는 떼지 않고, 그 공고의 상세를 열거나 원문 링크를 누르면 확인한 것(`posting_views`, 계정별)으로 보고 뗍니다.
    - 상단 `공고` 메뉴 옆 빨간 숫자 = 최근 7일 변경된 즐겨찾기 공고 + 확인하지 않은 관심 회사 새 공고.
- **수집 기록** (`/runs`): 상단에 채용 플랫폼별 카드, 그 안에 크롤러별 최근 30회(사람인은 일반 공고·헤드헌팅 그래프를 나란히, 발견 건수 규모가 달라 축을 따로 씀. 성공률, 평균 소요, 최근 발견 건수, 발견 공고 추이 선 그래프, 회차별 신규·삭제 막대, 실행 상태 띠, 올리면 회차별 자세한 값 — `static/runs.js`), 아래에 실행 기록 표(50건씩 페이지, 검색 조건 필터 유지). 발견 추이는 끝까지 돈 실행(성공·부분)만 잇고, 첫 수집(발견 공고가 모두 신규)은 막대 눈금에서 빼고 잘라 표시합니다.
- **설정**: 상단은 키워드·지역 등록·삭제와 `필터 생성`, 하단은 사이트별 검색 필터 파일의 내용(직무·지역 등 조건, 최대 페이지, 파일 수정 시각, 마지막 생성 기록)을 수집 상태와 같은 카드 모양으로 보여줍니다. 직무 값은 매핑 데이터의 이름과 함께 표시합니다.
- **검색엔진 차단**: `/robots.txt`가 모든 수집을 금지하고(`Disallow: /`), 모든 응답에 `X-Robots-Tag: noindex, nofollow, noarchive` 헤더와 페이지마다 같은 robots 메타 태그를 붙여 외부 링크로 들어온 경우에도 색인되지 않게 합니다.
- **개인정보처리방침·서비스 이용약관** (`/privacy`, `/terms`): 푸터에서 열리고 로그인 없이 볼 수 있습니다. 구글 OAuth 동의 화면의 개인정보처리방침·서비스 약관 링크로 이 두 주소를 등록합니다. 운영자 표기·연락처·시행일은 `web/app.py`의 `LEGAL`에 있고, 수집하는 정보나 쿠키가 바뀌면 `templates/privacy.html`도 함께 고쳐야 합니다.
- **로그인 (구글)**: 설정 > 사용자 관리에서 `로그인 사용`을 켜고 끕니다(확인 모달). 켜져 있으면 `지금 수집` 버튼과 설정 메뉴는 **관리자로 로그인한 경우에만**, 연봉·인원 메뉴는 **로그인한 경우에만**(등급 무관) 보이고 쓸 수 있습니다(직접 요청해도 막힘). 꺼져 있으면 모두 제한 없이 쓸 수 있습니다. 공고·수집 기록은 로그인과 관계없이 볼 수 있습니다.
  - 회원가입은 없습니다. 구글로 처음 로그인하면 자동 가입되고 등급은 `일반`입니다.
  - 관리자: `config.yaml`의 `auth.admin_emails`(항상 관리자, 화면에서 변경 불가) + 설정 > 사용자 관리에서 `관리자`로 바꾼 사용자. 내 등급은 바꿀 수 없습니다.
  - 켜려면 `config.yaml`의 `auth`에 구글 OAuth 클라이언트 ID·시크릿을 넣고, 관리자 계정으로 먼저 로그인해야 합니다(켠 뒤 아무도 관리할 수 없게 되는 일을 막기 위해). 구글 클라우드 콘솔에서 웹 애플리케이션용 OAuth 클라이언트를 만들고 리디렉션 URI `<접속 주소>/auth/callback`을 등록하세요. **구글은 https 도메인 주소만 허용합니다** (http는 localhost만 예외, IP 주소 불가).
  - 로그인 유지는 JWT 두 개를 HttpOnly·SameSite=Lax 쿠키(https 접속이면 Secure)에 담아 합니다 (`web/tokens.py`). 서명 키는 처음 실행 때 만들어 DB(`app_settings`)에 둡니다.
    - **Access**(`rc_access`, 15분): 서명만 확인합니다. 만료되면 요청을 받을 때 서버가 Refresh로 새로 발급해 응답 쿠키에 넣습니다(화면 JS는 토큰을 다루지 않음).
    - **Refresh**(`rc_refresh`, 14일): 쓸 때마다 새 토큰으로 바꾸고 만료를 14일 늘립니다. 로그인한 때부터 최대 60일이 지나면 다시 로그인해야 합니다. 로그인 한 번(기기 하나)마다 `login_sessions`에 기록합니다.
    - 이미 바뀐 옛 Refresh가 1분 안에 다시 오면 동시에 보낸 요청으로 보고 지금 토큰을 다시 주고, 그 뒤에 오면 토큰이 새어 나간 것으로 보고 그 로그인을 끊습니다.
    - 설정 > 사용자 관리의 **로그인 기기**에 사용자별로 로그인 중인 기기(User-Agent로 추정한 종류 아이콘 PC·휴대폰·태블릿·알 수 없음, 알 수 있으면 기종 — 예: 갤럭시 SM-S928N, iPhone, Windows PC — 과 운영체제·브라우저. 요즘 크롬은 안드로이드 기종을 가려 보내 'Android 휴대폰'으로, iPadOS 사파리는 Mac과 같은 UA라 Mac으로 보입니다), 로그인 시각, 로그인 IP, 최근 사용(토큰을 마지막으로 바꾼 때, 15분 단위)을 보여줍니다. 기기마다 `로그아웃`, 사용자마다 `모두 로그아웃`이 있습니다.
    - 로그인하면 화면 오른쪽 위에 **사용자 메뉴**(구글 프로필 사진 — 없거나 못 불러오면 이름 첫 글자 — 와 이름)가 보이고, 누르면 `마이페이지`와 `로그아웃`이 나옵니다(바깥 클릭·Esc로 닫힘, `static/usermenu.js`). 로그인한 사용자는 누구나 **마이페이지**(`/me`)에서 프로필 카드(사진·이름·등급·이메일·가입·최근 로그인)와 내 로그인 기기를 보고, 기기별 `로그아웃`과 `다른 기기 모두 로그아웃`(지금 기기는 유지)을 할 수 있습니다. 다른 사용자의 기기는 끊을 수 없고, 지금 쓰는 기기를 로그아웃하면 이 브라우저도 로그아웃됩니다. 기기 목록은 설정과 같은 템플릿(`templates/_devices.html`)을 씁니다.
    - 로그아웃하거나 위 버튼을 누르면 그 로그인을 DB에서 끊어, 복사된 Access 토큰도 바로 못 씁니다.

## 이력서 (`/resumes`)

로그인한 사용자는 누구나 오른쪽 위 사용자 메뉴의 `이력서`(마이페이지와 로그아웃 사이)에서 이력서 양식(템플릿)을 직접 만들어 공유하고, 그 양식으로 이력서를 작성해 PDF로 내려받습니다. 탭은 `내 이력서 | 템플릿 | 위젯`입니다.

- **위젯**: 이력서의 항목 하나. 종류는 입력 항목(form)·제목·고정 문구·구분선입니다. 입력 항목은 입력 칸 목록을 가지며 칸마다 이름, 종류(한 줄 글·여러 줄 글·연월·날짜·목록에서 선택·태그·이메일·전화번호·링크·숫자), **힌트**(입력 칸에 흐리게 보이는 안내), **예시 텍스트**(이 템플릿으로 이력서를 만들면 미리 채워지는 내용), 도움말, 너비(12칸 중 몇 칸), 필수 표시, 강조(문서에서 크게)를 정합니다. `여러 개 입력`을 켜면 경력·학력처럼 항목을 반복해 적습니다.
- **문서 표시 형식**(입력 항목 위젯마다): `기본`(이름 아래 값, 너비대로 배치), `프로필`(이름 크게 + 배지, 회색 부가정보 줄, `이메일 … | 휴대폰 …`), `목록`(왼쪽 기간 + 오른쪽 굵은 제목·회색 부가정보·배지·본문), `카드`(칸마다 상자로 나란히, 첫 줄 굵게), `왼쪽 제목`(위젯 제목을 왼쪽에, 경력기술서처럼). 프로필·목록·왼쪽 제목에서는 입력 칸마다 **문서 위치**(제목·부가정보·배지·왼쪽 기간·이름·값 한 줄·이름: 값·본문)를 정하고, `문서에서 이름 숨기기`도 고릅니다. 목록은 왼쪽 기간 자리의 연월·날짜 두 칸을 `시작 ~ 끝`으로 잇고(끝이 비면 `현재`), `항목마다 기간`(시작·끝 달 포함, 2021.08~2026.02 = 4년 7개월)과 `제목 옆에 기간 합계`(겹치는 기간은 한 번만)를 켤 수 있습니다. 제목 모양은 밑줄·굵은 윗선 + 큰 제목·굵은 글씨만 중에서 고릅니다. 편집기는 고른 표시 형식에서 쓰는 옵션만 보여 줍니다(예: `문서에서 크게`는 기본 형식에서만, 기간 옵션은 목록 형식에서만). 예시 텍스트도 칸 종류에 맞게 고릅니다(목록에서 선택은 선택지 중에서, 연월·날짜는 날짜 선택기로).
- **기간 입력·전화번호·이메일**: 연월·날짜 칸은 한 날짜 또는 `기간으로 입력`(시작 ~ 끝, 값 `YYYY-MM~YYYY-MM`)을 고르고, 기간이면 `시작과 끝이 같아도 됨`(기본 켬)과 `끝을 비우면 '현재'`(재직·재학·진행 중)를 정합니다. 작성 화면에서 시작을 고르면 끝 달력은 그 뒤만, 끝을 고르면 시작은 그 앞만 고를 수 있고, 직접 친 값은 순서를 검사해 칸 아래에 알려 줍니다. 기본 위젯의 경력(재직기간)·학력(재학기간)·경험/활동/교육(기간)은 기간 칸 하나를 씁니다(예전에 만든 템플릿·이력서의 시작·끝 두 칸도 문서·검사가 그대로 동작). 전화번호는 숫자만 저장하고(`tel_digits`), 입력 칸과 문서에서만 하이픈을 붙여 보여 줍니다(`format_tel`, 010-1234-5678, 02-123-4567, 031-123-4567, 0505-…, 1588-1234; `+82` 같은 국제번호나 글이 섞인 값은 적은 그대로). 이메일은 형식을 검사합니다. 틀린 칸이 있어도 자동 저장은 하되(쓰던 내용을 잃지 않게) 상태에 `확인할 칸 n개`를 보이고, 미리보기·PDF는 그 칸으로 이동하며 막습니다.
- **제목·고정 문구·구분선 위젯 옵션**: 제목은 크기(크게·보통·작게)와 정렬, 고정 문구는 정렬(기본 가운데, 줄바꿈 그대로), 구분선은 굵기(얇게·보통·굵게)·모양(실선·파선·점선)·위아래 여백(좁게·보통·넓게)을 정합니다.
- **스타일 (글꼴·글자 크기·색)**: 템플릿 편집기에서 위젯을 고르지 않으면 오른쪽에 `문서 스타일`이 나옵니다. 템플릿 전체의 글꼴, 본문 글자 크기(pt, 기본 8.7pt = 사람인, 7~12pt; 이름·제목 등 다른 글자도 같은 비율로), 색 5가지(본문, 제목·이름, 보조 글자, 강조, 선·테두리)를 정하고 `layout.theme`에 기본값과 다른 것만 저장합니다. 위젯마다 `스타일`에서 그 위젯만 글꼴·글자 크기(템플릿 크기의 80~150%)·색(입력 항목: 글자·제목·선, 제목·고정 문구: 글자, 구분선: 선)을 바꿀 수 있고(`config.style`), 비워 두면 템플릿을 따릅니다. 굵은 윗선·배지·연한 태그 테두리처럼 따로 고르지 않는 색은 고른 색에서 만듭니다. 문서는 글자 크기를 `calc(사람인 크기 × var(--k))`, 색을 CSS 변수로 쓰므로 기본값이면 사람인과 똑같고, PDF(WeasyPrint)도 같게 나옵니다.
- **색 선택기**(`static/colorpicker.js`, 공용): 색 견본을 누르면 색 영역(채도·밝기)·색상 막대·자주 쓰는 색 16개·스포이드(지원하는 브라우저)로 고르고, 입력 칸에 `#`으로 시작하는 색 코드(`#1a2b3c`, `#abc`, `#` 없이도 됨)를 바로 쳐도 됩니다. 잘못된 코드는 빨간 테두리로 알려 주고 반영하지 않습니다. 휴대폰에서는 아래에서 올라오는 시트로 열립니다. 서버도 `#rrggbb`만 받아(`resumes.color`) 문서의 style 속성에 다른 글이 들어가지 않습니다.
- **기본 위젯·템플릿 (사람인 기준)**: 사람인 이력서의 항목 구성(사람인 개인정보처리방침의 이력서 항목)과 문서 모양을 따른 위젯 16개(인적사항, 요약 카드, 간략 소개, 나의 스킬, 경력, 경력기술서, 학력, 경험/활동/교육, 자격증, 어학시험, 수상내역, 포트폴리오, 취업 우대사항, 희망근무조건, 자기소개서, 구분선)와 `기본 이력서` 템플릿 하나를 넣어 둡니다(`web/resumes.py`의 `BUILTIN_WIDGETS`·`BUILTIN_TEMPLATES`). 시작할 때 최신 정의로 맞추고, 정의에서 빠진 예전 기본 위젯·템플릿은 지웁니다(이미 복사해 쓴 템플릿·이력서는 그대로). 누구도 고칠 수 없고 복사해서 씁니다. 사진·포트폴리오 파일은 첨부파일 위젯이 생기면 추가하고, 취업 우대사항의 장애 여부는 민감정보라 넣지 않았습니다. 요약 카드는 다른 항목에서 계산하지 않고 직접 적습니다.
- **템플릿 편집기**(`/resumes/templates/{id}/edit`, `static/resume_builder.js`): 행을 위에서 아래로 쌓고, 한 행을 가로로 최대 4칸(12칸 격자)으로 나눕니다. 왼쪽 위젯 목록에서 칸 안이나 행 사이로 끌어다 놓고(행 사이에 놓으면 새 행), 배치한 위젯도 끌어서 옮깁니다. 칸 사이 손잡이를 끌거나 −/+로 칸 너비를 바꿉니다. 터치 화면은 `추가`(맨 아래 새 행)와 ↑↓ 버튼을 씁니다. 위젯을 누르면 오른쪽에서 설정을 고치고(`← 문서 스타일`로 템플릿 전체 스타일로 돌아감), `내 위젯으로 저장`/`원본 위젯에 반영`으로 위젯 목록에 저장해 다른 템플릿에서 조합합니다. `미리보기`는 저장하지 않은 지금 상태를 새 창에 문서로 보여 줍니다(`POST /resumes/preview`, 위젯 편집 화면도 같음). Ctrl+S로 저장합니다.
- **사용법 안내**(`static/resume_tour.js`): 템플릿·위젯 편집 화면을 처음 열면 단계별 둘러보기가 한 번 자동으로 뜹니다(이름·설명·공개 → 위젯 목록 → 행·칸 → 위젯 설정 → 문서 스타일 → 미리보기·저장 / 위젯은 제목·반복 → 표시 형식 → 입력 칸 → 힌트·예시 텍스트·도움말 → 스타일 → 미리보기). 실제 화면 요소를 강조하고 설명을 띄우며, 휴대폰(600px 이하)은 아래 시트로 보여 주고 강조한 곳이 시트에 가리지 않게 스크롤합니다(떠 있는 `+ 위젯` 버튼은 시트를 위로). 안내하는 동안에는 사용자가 페이지를 스크롤할 수 없습니다(휠·터치·키보드·스크롤바, 안내가 강조할 곳으로 옮기는 스크롤만 됨). 위쪽 `? 사용법`으로 다시 보고, ←/→/Esc로 움직입니다. 본 기록은 브라우저(localStorage, 템플릿·입력 항목 위젯·그 밖의 위젯 따로)에 남깁니다. 편집 내용은 바꾸지 않습니다. 목록의 템플릿·위젯 탭에는 `처음이라면: 만드는 순서` 안내가 있습니다(내 것이 없으면 펼쳐 둠).
- **복사 원칙**: 템플릿에 넣은 위젯은 그때의 설정을, 이력서는 만든 때의 템플릿 배치를 복사해 둡니다. 원본 위젯·템플릿을 고치거나 지워도 이미 만든 템플릿·이력서는 바뀌지 않습니다.
- **공유**: 템플릿·위젯마다 비공개(나만)·공개(로그인한 모든 사용자가 보고 복사, 만든 사람은 표시 안 함)를 고릅니다. 이력서 내용은 항상 본인만 봅니다. 다른 사람의 것은 주소를 알아도 열거나 고칠 수 없습니다(404).
- **날짜 선택기**(`static/datepicker.js`, 공용): 연월·날짜 칸은 달력으로 고릅니다(제목을 누르면 월 → 연도 단위로 넓혀 빨리 이동, 방향키·Enter·Esc, 휴대폰은 아래에서 올라오는 시트). 직접 쳐도 되며(2021.8, 202108, 2021.08.15 등) 잘못된 값은 빨갛게 표시합니다. 값은 `YYYY-MM`/`YYYY-MM-DD`로 저장하고 화면에는 `2021.08`로 보입니다. 다른 화면에서는 `DatePicker.attach(input, {mode, onChange})` 또는 `<input data-datepicker="month|date">`로 씁니다.
- **만 나이**: 날짜 칸에 `문서에 출생연도와 만 나이로`를 켜면(기본 인적사항의 생년월일) 문서에 `1999 (26세)`처럼 보입니다. 오늘(한국 시간) 기준 만 나이이며, 달력은 연도부터 열리고 오늘 이후는 고를 수 없습니다.
- **주소 검색**(`static/address.js`, 공용): 입력 칸 종류 `주소`는 옆의 `주소 검색`으로 카카오 우편번호 서비스(키 필요 없음)를 열어 `(우편번호) 도로명 주소`를 채우고, 이어서 상세 주소를 적게 합니다. 카카오 스크립트는 처음 검색할 때만 불러옵니다(개인정보처리방침에 안내). 다른 화면에서는 `<input data-address-search>`로 씁니다.
- **위젯 바로 추가**: 템플릿 편집기의 빈 칸(`+ 위젯 추가`)을 누르면 위젯을 이름·항목으로 찾아 그 칸에 바로 넣습니다(PC·휴대폰). 태블릿·휴대폰(폭 1100px 이하)에서는 위쪽 위젯 목록 대신 떠 있는 `+ 위젯` 버튼으로 찾아 넣고, 위젯을 고른 상태면 그 아래에, 아니면 맨 아래 새 행으로 놓입니다.
- **이력서 작성**(`/resumes/{id}/edit`, `static/resume_editor.js`): 템플릿 배치대로 입력 칸을 보여 주고, 입력을 멈추면 1.2초 뒤 자동 저장합니다. 반복 위젯은 항목 추가·삭제·순서 변경을 합니다.
- **PDF 다운로드 버튼**(`static/pdf_download.js`, 작성·목록·미리보기 공용, `data-pdf-download`): 페이지를 옮기지 않고 그 자리에서 받아 내려받기를 시작하며, 버튼에 `PDF 만드는 중…`(회전 표시) → `✓ 다운로드 완료`를 보이고 실패하면 이유를 토스트로 알립니다(작성 화면은 바뀐 내용을 먼저 저장). 링크로 이동하면 파일만 받고 페이지는 그대로라 상단 진행 표시가 꺼지지 않던 문제를 막습니다.
- **미리보기·PDF**: 같은 문서 HTML(`templates/resume_doc.html`, A4)을 화면과 PDF가 함께 씁니다. 행은 표로 가로 칸을 나누고, 입력 칸은 순서대로 12칸씩 줄을 채워(편집 화면과 같은 규칙) 빈 칸도 자리를 지키며, 모두 빈 줄·항목은 뺍니다. 글꼴·크기·색·간격은 사람인 이력서 PDF에서 잰 값과 같습니다(사람인 화면 px × 0.5808 = pt, 예: 본문 15px = 8.71pt, 여백 28pt). 글꼴은 기본 Pretendard(Regular·SemiBold·Bold)이고, 스타일로 나눔고딕·IBM Plex Sans KR·나눔명조·고운바탕을 고를 수 있습니다(모두 SIL OFL, `static/fonts`에 라이선스 파일과 함께 woff2로 두고 화면과 PDF가 같이 씀). 문서에는 그 문서에서 쓰는 글꼴만 넣습니다. PDF는 서버에서 WeasyPrint로 만듭니다. 도커 이미지에 Pango와 대체 한글 글꼴(Noto Sans CJK)을 설치하므로(이미지 약 570MB), 도커 없이 실행하면 PDF 다운로드는 그 라이브러리를 따로 설치해야 동작합니다.
- **제한**: 사용자당 이력서 50개·템플릿 50개·위젯 200개, 한 행 최대 4칸, 위젯당 입력 칸 30개, 반복 항목 50개.
- **첨부파일 위젯(사진 등)**: 아직 없습니다. 추가할 때는 `FIELD_TYPES`에 종류를 더하고 파일은 별도 테이블에 저장한 뒤, 이력서 값에는 파일 ID만 넣습니다(`normalize_value`에서 형식 검사). 그때 개인정보처리방침의 처리 항목도 고칩니다.

## 삭제 판정 규칙

"사라졌다"는 "검색 결과에서 안 보였다"로만 알 수 있으므로 판정은 **검색 조건(검색 필터 파일의 `searches[].name`) 단위**로 하고, 잘못 삭제하지 않도록 보수적으로 동작합니다.

1. 마지막 페이지까지 오류 없이 수집한 실행(`SUCCESS`)에서만 판정합니다. 오류, `max_pages` 도달, 수집 중 전체 건수 변경(`PARTIAL`)이면 추가·갱신만 하고 판정은 건너뜁니다.
2. `sync.missing_threshold`회 **연속**으로 보이지 않아야 그 검색 조건과의 연결을 끊습니다. 수집 도중 페이지가 밀려 일시적으로 누락된 공고를 오삭제하지 않기 위해서입니다.
3. 한 공고가 여러 검색 조건에 걸려 있으면 **모든 조건에서 빠졌을 때만** `DELETED`가 됩니다.

> 마감된 공고도 검색 결과에서 빠지므로 `DELETED`가 됩니다. 마감과 실제 삭제를 구분하려면 상세 페이지 확인이 필요합니다.

## 새 채용 사이트 추가

1. `crawlers/<site>.py`에 `Condition`을 상속한 dataclass(그 사이트의 검색 조건과 URL 파라미터 매핑)와 `Crawler`를 상속한 클래스(`site`, `condition_class`, `fetch_page`)를 만듭니다.
2. `crawlers/__init__.py`의 `CRAWLERS`에 등록합니다.
3. `config/searches/<site>.yaml`을 만들어 `searches`에 조건을 추가합니다.
4. (선택) 키워드 필터 생성을 지원하려면 `job_filter_field`와 `fetch_job_options()`(직무 선택지 목록)를, 지역 필터 생성을 지원하려면 `region_filter_fields`와 `fetch_region_options()`(지역 선택지 목록)를 구현합니다.

검색 조건은 사이트마다 분류 체계와 코드가 다르므로 크롤러마다 자기 `Condition`을 정의합니다. 설정에 알 수 없는 키가 있으면 시작할 때 에러가 납니다. 정의되지 않은 파라미터는 `params`로 그대로 전달할 수 있습니다.

## 상세 페이지 수집으로 확장할 때

지금은 목록 정보만 수집하고 상세 링크는 `job_postings.detail_url`에 저장합니다. 상세 수집을 붙인다면:

- `Crawler`에 `fetch_detail(detail_url)`을 추가하고 사이트별로 구현
- `job_postings`와 1:1인 `job_posting_details` 테이블(본문, 수집 시각)을 추가
- `posting_events`의 CREATED / UPDATED / REACTIVATED 이벤트가 생긴 공고만 상세를 가져오면 요청 수를 최소화할 수 있음

## 주의

- 사이트 구조가 바뀌면 파서가 `ParseError`를 내고 해당 실행은 `FAILED`가 됩니다(이때 삭제 판정은 하지 않음). `crawl_runs`를 확인하세요.
- 각 사이트의 robots.txt를 확인해 허용된 경로만 요청합니다(현재 두 사이트의 검색 경로는 허용됨). 요청 간 지연(`http.delay_seconds`)을 너무 줄이지 마세요.
- 사람인은 근무지가 여러 곳인 공고의 경우 그중 하나만 서울·경기여도 검색되고, 목록에는 첫 번째 근무지만 표시됩니다. 그래서 서울·경기 필터에도 "충남 아산시" 같은 공고가 보일 수 있습니다.
- 잡코리아는 500페이지(10,000건)까지만 제공하므로, 결과가 그보다 많은 조건은 끝까지 볼 수 없어 삭제 판정이 되지 않습니다. 조건을 더 좁히세요.
